Software Supply Chain Guardian

Paste a GitHub link. The Guardian lists every library the app depends on, finds the ones with known security holes or suspicious changes, rates each one, and attaches proof from a real tool to every finding.

Overview Architecture, step by step

Three questions it answers

What is in the app?Every library, its exact version, and the chain of libraries that pulled it in.
What changed?New libraries, new install scripts, unpinned Docker images and CI steps.
What looks risky?Known security holes (CVEs), rated Critical to Low, each with a fix version and proof.

How it works, in one minute

  1. Get the dependency files. From a GitHub link it downloads only the files that list libraries (lockfiles, Dockerfiles, CI files). No full clone.
  2. Make the ingredients list. Syft writes an SBOM: every library with a universal name tag (purl), for any language.
  3. Draw the family tree. Who pulled in whom, so each problem shows the path from your app to the bad library.
  4. Look for problems. Two scanners (Grype and OSV) check for known holes. Six small checks look for suspicious changes.
  5. Rate each finding. A fixed rule table gives Critical, High, Medium or Low. Same input, same answer, every time.
  6. Explain it (optional AI). An AI writes plain-English explanations. Code checks every claim and rejects anything without proof.
  7. Show the report. The web page shows the results. JSON files keep the full record for machines.

How a risk level is chosen

Rules are read top to bottom and the first match wins. Each finding records its rule ID, so anyone can see why it got its level.

RuleWhen it matchesLevel
R-MALKnown malicious package (OSV MAL- entry)Critical
R-CVE-1 … 4CVE with Critical / High / Medium / Low severityCritical to Low
R-CVE-UCVE with unknown severity (marked under investigation)Medium
R-AN-1Look-alike package name, or an install script addedHigh
R-AN-2Unexpected new library, or Docker image on latestMedium
R-AN-3Version bump, or CI step not pinned to an exact commitLow

A library used only by developers (not shipped) drops one level. A fuzzy name match lowers confidence. The tool never says "safe".

Why you can trust it

Guardrails

  • Every finding points to the exact spot in a scanner's raw, untouched output, with a file fingerprint (sha256).
  • Two scanners. When both agree, the finding says confirmed_by: grype, osv.
  • Risk comes from fixed rules, never from the AI.
  • The AI can only explain. A fake CVE planted in its answer is rejected, with the reason shown.
  • Text inside the scanned repo is treated as untrusted data, so planted instructions do nothing.
  • The scan works fully with the AI switched off.

Known limits today

  • Tested end to end on npm and Ruby. Other languages go through the same path but are not yet demoed.
  • Look-alike name and install-script checks are npm only.
  • OSV needs internet at scan time. Grype works offline.
  • "What changed" needs git history, so it works from the command line, not yet from a pasted link.
  • Juice Shop has no lockfile on GitHub, so a pasted link finds fewer libraries than a local scan.
  • "Is the bad code actually called?" is not checked yet.

Short forms

SBOMSoftware Bill of Materials: the ingredients list of an app.
purlA universal name tag for a library, e.g. pkg:npm/express@4.21.0.
CycloneDXA standard file format for SBOMs.
LockfileFile that pins every exact version, e.g. package-lock.json, Gemfile.lock.
CVE / GHSAPublic IDs for a known security hole. One hole can have both.
Direct / transitiveDirect: your app chose it. Transitive: another library pulled it in.
EvidenceA pointer to the exact place in a tool's raw output that backs a finding.
ValidatorPlain code that checks every AI claim against the evidence.
PinningReferring to an image or CI step by exact hash so it cannot change silently.

Every step explained

1

Web UI

Bosch_Guardian_Clean/frontend

You paste a GitHub URL and, if you want, a branch, tag or commit. While the scan runs, the page shows which stage it is on. When it finishes, it shows counts by risk, each finding with its path and proof, and download buttons for the SBOM and the report.

URL + ref→request to the API
2

API server

backend/app/main.py

POST /scan answers right away with a scan ID and starts the scan in the background, so the page never freezes. The page asks GET /scan/{id} for progress, then reads /result, /graph, /sbom and /report.

URL + ref→scan ID + background job
3

Fetch dependency files

guardian/fetch.py · guardian/prepare.py

The GitHub API turns the branch or tag into one exact commit, then downloads only the files that describe dependencies: lockfiles, manifests, Dockerfiles and CI workflows. The app's own source code is never downloaded.

This is fast even on very large repos, and the commit ID pins exactly what was scanned. A GITHUB_TOKEN raises GitHub's limit from 60 to 5,000 requests an hour.
URL + ref→small folder of files + commit SHA
4

Resolve

guardian/resolve/

Finds each lockfile and reads it with a parser for that ecosystem, for example Gemfile.lock for Ruby. The parser lists every parent→child link ("actionpack needs rack-session"). Nothing is installed and no package code runs.

Malicious packages hide code in install scripts, so we only read files. Adding a language means adding one parser here.
lockfiles→edges
5

Build SBOM

guardian/sbom.py

Syft, run in Docker from an image pinned by digest, lists every component with its exact version and a purl. Step 4's edges are merged in, and each lockfile gets a root node that stands for the app.

pkg:npm/jsonwebtoken@0.4.0
pkg:gem/actionpack@7.0.4
pkg:pypi/django@4.2
files + edges→sbom.cdx.json
Language boundary. From step 6 on, the code sees only purls in CycloneDX. It does not care whether the app is JavaScript, Ruby, Java or Go.
6

Dependency graph

guardian/graph.py

Each library is a dot and each edge an arrow. For every library it finds the shortest route from the app, and counts how many routes reach it.

app → importmap-rails → actionpack → rack-session
Your app never chose rack-session. The path shows which direct library to upgrade.
SBOM→graph.json, paths
7

CVE scanners

guardian/scanners/grype.py · osv.py

Grype checks every purl against its local vulnerability database and records the date that database was built. OSV-Scanner checks the same SBOM against the live OSV service, which also lists known malicious packages. Each tool's raw output is saved untouched with its fingerprint.

SBOM→raw/grype.json, raw/osv.json
8

Six detectors

guardian/detectors/

Small checks for problems that have no CVE yet:

CheckLooks for
typosquatA direct library named one or two letters away from a popular one (top 5,000 npm names)
install_scriptA package that runs code when installed
image_pinDockerfile FROM node:latest or a tag without @sha256
ci_pinA GitHub Actions step on a movable tag like @main
sbom_diffLibraries added or changed since the last scan
git_diffChanged lines in lockfiles, Dockerfiles and CI files
SBOM + files + git history→suspicious-change findings
9

Merge, then rate risk

guardian/scanners/merge.py · guardian/risk.py

If both scanners report the same hole for the same library (even under two names, CVE and GHSA), it becomes one finding marked confirmed_by: grype, osv. Each finding gets its path from step 6. Then the fixed rule table sets the level and records the rule ID.

jsonwebtoken@0.4.0 · CVE-2015-9235 · severity Critical
→ rule R-CVE-1 → Critical · confirmed by grype + osv
findings→rated findings
10

AI review + validator

guardian/ai/

Only runs if an AI provider is configured. It gets the top 20 findings, never the whole SBOM. Three AI steps write claims: explain the CVEs, explain the changes, and a short inventory note. Each claim must cite evidence IDs. The validator, which is plain code, checks every CVE ID, name and version against that evidence and rejects mismatches with a reason. The summary uses accepted claims only.

Repo text is marked untrusted, secrets are removed before sending, and each AI call has a 30-second limit. If the AI is off or fails, the scan still completes and this section says "unavailable".
top 20 findings→accepted + rejected claims
11

Coverage + report

guardian/coverage.py · guardian/report/

Writes the result files. If one stage fails, the scan is marked "partial" and the other stages' results are kept.

FileWhat it holds
findings.jsonEvery finding with level, rule, path, fix version and evidence. The source of truth.
coverage.jsonEach check per language: finding, pass, not covered, or error. Zero libraries shows as a warning.
run.jsonTool versions, database dates, timings and status of each stage.
sbom.cdx.jsonThe ingredients list from step 5.
report.htmlA one-file report for people.
